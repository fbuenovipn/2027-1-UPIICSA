Módulo 1

Arquitectura de Apache Hadoop

Procesamiento distribuido sobre commodity hardware

Historia y motivación

  • 2003: Google publica paper sobre Google File System (GFS)
  • 2004: Google publica paper sobre MapReduce
  • 2006: Doug Cutting + Mike Cafarella crean Hadoop en Yahoo, basado en ambos papers
  • El nombre: elefante de juguete del hijo de Doug Cutting
  • Hoy: Apache Software Foundation, miles de empresas

El problema que resuelve: 1 petabyte de logs. Una computadora = 2 semanas. 1,000 computadoras modestas = 2 horas.

Los 3 pilares

HDFS — Hadoop Distributed File System

  • Divide archivos en bloques (128 MB default)
  • Replica cada bloque 3 veces en nodos distintos
  • NameNode: directorio maestro con metadatos
  • DataNodes: almacenan bloques reales

MapReduce — procesamiento paralelo

  • Map: aplica función a cada fragmento en paralelo
  • Shuffle: agrupa resultados intermedios por clave
  • Reduce: combina en respuesta final

YARN — gestor de recursos del clúster (v2.x+)

[Cliente] ↓ solicitud [NameNode] ←→ [Secondary NameNode — backup] ↓ coordina ubicación de bloques [DataNode 1] [DataNode 2] [DataNode 3] ··· [DataNode N] (bloque A, C) (bloque A, B) (bloque B, C) (réplicas)
Metáfora
🏦

Hadoop es un banco con miles de empleados modestos. En lugar de contratar un genio que resuelve todo (supercomputadora a $10M), contratas 1,000 empleados normales ($1,000 c/u). Cada uno resuelve su parte del problema, un coordinador combina los resultados. La replicación HDFS es como guardar 3 copias del testamento en distintas notarías: si una se incendia, el documento no se pierde.

CASO REAL

Yahoo — El caso de uso que creó Hadoop

Yahoo tiene más de 40,000 nodos Hadoop procesando 170 petabytes/mes: ranking de búsqueda, detección de spam, perfiles de publicidad y análisis de clics. Todo corriendo sobre servidores de uso general — la misma tecnología que cualquier empresa puede replicar hoy en la nube.

Módulo 2

Comandos HDFS

Gestionar el sistema de archivos distribuido desde la línea de comandos

Fundamentos

HDFS usa una interfaz de línea de comandos similar a Unix/Linux. El comando base es hdfs dfs -<comando>.

Los archivos en HDFS se acceden con la URI:
hdfs://namenode:9000/ruta/archivo

La principal diferencia con Unix: los comandos operan sobre un sistema de archivos distribuido que puede estar repartido entre cientos de máquinas en la red.

Conexión SSH al clúster

  • Conexión básica: ssh usuario@namenode.cluster
  • Con clave privada (AWS/Azure): ssh -i ~/.ssh/key.pem hadoop@ec2-xx.aws.com
  • Túnel para UI HDFS (puerto 9870): ssh -L 9870:localhost:9870 usuario@namenode
  • Luego abrir: http://localhost:9870
comandos_hdfs.sh
# ===== NAVEGACIÓN =====
hdfs dfs -ls /user/datos/          # listar directorio
hdfs dfs -ls -R /user/datos/       # recursivo
hdfs dfs -mkdir /user/proyecto     # crear directorio
hdfs dfs -mkdir -p /user/raw/2024  # crear con padres

# ===== TRANSFERENCIA =====
hdfs dfs -put datos.csv /user/proyecto/raw/       # local → HDFS
hdfs dfs -copyFromLocal datos.csv /user/proyecto/ # equivalente
hdfs dfs -get /user/proyecto/result.csv ./local/  # HDFS → local

# ===== OPERACIONES =====
hdfs dfs -cat /user/proyecto/datos.csv   # ver contenido
hdfs dfs -cp  /source/file.csv /dest/     # copiar en HDFS
hdfs dfs -mv  /user/raw/old.csv /archive/ # mover
hdfs dfs -rm  /user/temp/file.csv         # eliminar archivo
hdfs dfs -rm -r /user/temp/              # eliminar carpeta

# ===== INFORMACIÓN =====
hdfs dfs -du -h   /user/proyecto/        # tamaño por archivo
hdfs dfs -du -s -h /user/proyecto/       # tamaño total
hdfs dfsadmin -report                    # reporte del clúster
hdfs fsck /user/ -files -blocks          # verificar integridad

# ===== PERMISOS (Unix-like) =====
hdfs dfs -chmod 755 /user/proyecto/
hdfs dfs -chown hadoop:hadoop /user/proyecto/
Metáfora
💾

Los comandos HDFS son como Unix/Linux pero para un disco duro que existe en 1,000 computadoras simultáneamente. ls sigue siendo ls, mkdir sigue siendo mkdir — pero cuando haces put, tu archivo se divide en bloques y vuela a través de la red hacia docenas de máquinas al mismo tiempo, con 3 réplicas automáticas.

Módulo 3

Microsoft Azure HDInsight

Hadoop y Spark totalmente gestionados en la nube

¿Qué es HDInsight?

Servicio PaaS de Microsoft que despliega clústeres Hadoop/Spark completamente gestionados: sin instalar software, sin parchear servidores, sin administrar redes.

Tipos de clúster: Hadoop, HBase, Spark, Kafka, Interactive Query (Hive LLAP), Storm.

Ventajas: alta disponibilidad automática, escalado dinámico, integración nativa con Azure Data Lake, Synapse y Power BI.

Arquitectura HDInsight

  • Head Nodes × 2 (Alta Disponibilidad) — NameNode + ResourceManager
  • Worker Nodes × n — DataNode + NodeManager, escalables
  • Edge Node (opcional) — Jupyter, RStudio Server, acceso cliente
  • ADLS Gen2 — almacenamiento desacoplado del cómputo (paga solo por datos, no por cluster parado)
  • Azure Monitor — logs y métricas del clúster
azure_hdinsight.sh
# 1. Autenticarse en Azure
az login

# 2. Crear grupo de recursos
az group create \
  --name rg-bigdata-curso \
  --location eastus

# 3. Crear Azure Data Lake Storage Gen2
az storage account create \
  --name adlsbigdata2024 \
  --resource-group rg-bigdata-curso \
  --kind StorageV2 \
  --hns true    # hierarchical namespace = ADLS Gen2

# 4. Crear clúster HDInsight con Spark
az hdinsight create \
  --name cluster-spark-curso \
  --resource-group rg-bigdata-curso \
  --type Spark \
  --version 4.0 \
  --http-password 'Admin@BigData2024!' \
  --http-user admin \
  --storage-account adlsbigdata2024 \
  --workernode-count 3 \
  --workernode-size Standard_D4_v2

# 5. Verificar estado del clúster
az hdinsight show \
  --name cluster-spark-curso \
  --resource-group rg-bigdata-curso \
  --query 'properties.clusterState'

# Alternativa local sin costo: Docker
docker network create hadoop-net
docker run -d --net=hadoop-net --name namenode \
  -p 9870:9870 bde2020/hadoop-namenode:2.0.0-hadoop3.2.1-java8
Metáfora
🏟️

Azure HDInsight es como rentar un estadio completo (con electricidad, seguridad y mantenimiento incluidos) en lugar de construir el tuyo. Pagas por el partido que juegas. Cuando termina la temporada, lo devuelves y dejas de pagar. Si mañana necesitas el doble de capacidad, está disponible en 15 minutos.

Módulo 4

Apache Hive y HiveQL

SQL sobre Hadoop — el poder del lenguaje que ya conoces a escala masiva

¿Qué es Hive?

Capa de abstracción SQL sobre Hadoop. Convierte queries HQL en jobs MapReduce, Tez o Spark. Creado por Facebook (2007), open-source en 2008.

Data Lake vs Data Warehouse:

  • Data Lake: todos los datos raw, schema al leer, flexible, barato
  • Data Warehouse: datos transformados, schema al escribir, optimizado para queries analíticas
  • Data Lakehouse: lo mejor de ambos (Apache Iceberg, Delta Lake)

Ventajas del particionamiento

Una tabla sin particionar de 2 TB: cada query escanea todo el dataset.

La misma tabla particionada por año + mes: una query por "enero 2024" escanea solo ~15 GB en lugar de 2 TB.

Formatos de almacenamiento:

  • ORC — columnar, compresión SNAPPY, el más rápido para Hive
  • Parquet — columnar, compatible con Spark/Flink/Athena
  • TextFile — legible, más lento, para datos raw
analisis_ventas.hql
-- Crear base de datos
CREATE DATABASE IF NOT EXISTS analitica_2024
  LOCATION '/user/hive/warehouse/analitica_2024.db';
USE analitica_2024;

-- Tabla externa (datos en HDFS, Hive gestiona metadatos)
CREATE EXTERNAL TABLE IF NOT EXISTS ventas_raw (
    id_venta    STRING, fecha      STRING,
    id_cliente  STRING, id_prod    STRING,
    cantidad    INT,    precio     DOUBLE,
    ciudad      STRING
) ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
  STORED AS TEXTFILE LOCATION '/data/ventas/raw/'
  TBLPROPERTIES ("skip.header.line.count"="1");

-- Tabla interna particionada y comprimida
CREATE TABLE ventas_procesadas (
    id_venta STRING, id_cliente STRING,
    id_prod  STRING, cantidad INT,
    precio DOUBLE,  total DOUBLE
) PARTITIONED BY (anio INT, mes INT, ciudad STRING)
  STORED AS ORC TBLPROPERTIES ("orc.compress"="SNAPPY");

-- Top 10 productos — Window functions avanzadas
SELECT
    ciudad, mes,
    SUM(total) AS ventas_mes,
    SUM(SUM(total)) OVER (
        PARTITION BY ciudad ORDER BY mes
    ) AS acumulado_ciudad,
    RANK() OVER (
        PARTITION BY mes ORDER BY SUM(total) DESC
    ) AS ranking_mensual
FROM ventas_procesadas
WHERE anio = 2024
GROUP BY ciudad, mes;
Metáfora
🗣️

Hive es el traductor entre tu lenguaje (SQL, que ya conoces) y el lenguaje de Hadoop (MapReduce, que es complejo). Tú hablas español, el intérprete traduce al chino, los resultados vuelven en español. Sin Hive, necesitarías escribir programas Java de 500 líneas para lo que en HQL son 10 líneas.

De Hadoop a la nube nativa: la evolución del procesamiento masivo

La evolución

Hadoop fue revolucionario en 2006 pero tiene limitaciones: lento (escribe en disco entre cada paso MapReduce), complejo de administrar y difícil de escalar dinámicamente. La industria evolucionó hacia alternativas más modernas.

pyspark_ventas.py
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, sum as spark_sum, avg, count

spark = SparkSession.builder \
    .appName("Analisis Ventas MX") \
    .config("spark.sql.shuffle.partitions", "200") \
    .getOrCreate()

# Leer desde HDFS o Azure Data Lake (lazy — no ejecuta aún)
df = spark.read.parquet("hdfs:///data/ventas/2024/")
print(f"Registros totales: {df.count():,}")

# Pipeline de transformaciones (lazy evaluation)
resultado = (df
    .filter(col("pais") == "Mexico")
    .withColumn("total", col("cantidad") * col("precio"))
    .groupBy("estado", "categoria")
    .agg(
        spark_sum("total").alias("ingresos"),
        avg("precio").alias("precio_prom"),
        count("*").alias("transacciones")
    )
    .orderBy(col("ingresos").desc()))

# Action: ejecuta TODO el plan de ejecución optimizado
resultado.show(20, truncate=False)
resultado.write.mode("overwrite") \
    .partitionBy("estado") \
    .parquet("hdfs:///output/resumen_ventas/")
Metáfora — Spark vs MapReduce
🧩

MapReduce resuelve un rompecabezas tomando piezas del suelo (disco), trabajando con ellas y devolviéndolas al suelo entre cada paso. Spark lo resuelve en una mesa (RAM): no se agacha entre piezas. Por eso es 100x más rápido.

Metáfora — BigQuery
🍕

BigQuery es Uber Eats para datos: no necesitas restaurante propio (servidor), no te importa cómo llega la comida (procesamiento distribuido invisible), solo pides (SQL query) y en segundos llega el resultado. Pagas por pedido, no por el restaurante.

Resultado: decisión de crédito en 3 segundos con 94% de precisión.

Proyecto Final

Pipeline Big Data — NYC Yellow Cab

Diseña e implementa un pipeline de datos a escala real

🚕 Análisis de Taxis en Nueva York

El NYC Taxi and Limousine Commission publica datos públicos de todos los viajes en taxi de Nueva York — más de 100 millones de registros anuales. Tu misión: construir un pipeline Big Data completo desde ingesta hasta visualización, comparando herramientas clásicas y modernas.

Fase 1: IngestaDescargar dataset NYC Yellow Cab (nyc.gov). Cargar en HDFS local con Docker usando comandos hdfs dfs.
Fase 2: HiveCrear base de datos con tablas particionadas por mes y zona. Ejecutar al menos 5 queries HQL de análisis.
Fase 3: SparkMigrar el mismo análisis a PySpark. Medir y comparar tiempos de ejecución: ¿cuánto más rápido?
Fase 4: AnálisisResponder: Top 5 zonas de mayor demanda, horas pico, correlación distancia/precio, patrones día de semana.
Fase 5: VisualDashboard en Power BI o Tableau con los hallazgos principales. Mapa de calor de zonas + serie temporal.
Fase 6: ReporteComparativa técnica: Hive vs Spark — velocidad, facilidad de uso, escalabilidad, costo.
El dato diferenciador: No es solo hacer que funcione — es entender por qué Spark supera a MapReduce en este caso, cuándo conviene usar BigQuery en lugar de Hive, y cómo el particionamiento de datos puede hacer la diferencia entre una query de 10 minutos y una de 10 segundos. Eso es pensar como ingeniero de datos.

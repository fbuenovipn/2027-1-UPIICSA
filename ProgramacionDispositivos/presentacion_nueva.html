⚡ ART vs Dalvik

Dalvik (hasta Android 4.x): Compilaba el código mientras lo ejecutaba — JIT (Just In Time). Como traducir un libro palabra por palabra mientras lo lees.

ART (desde Android 5.0): Compila el código antes de ejecutarlo — AOT (Ahead Of Time). Como haber traducido el libro completo antes de empezar.

Resultado: arranque más rápido y menor consumo de batería.

Kotlin — El lenguaje oficial de Android

¿Por qué Kotlin reemplazó a Java?

Kotlin es el lenguaje oficial de Android desde 2017. Su ventaja principal: hace lo mismo que Java con hasta un 40% menos de código, y el compilador detecta errores que en Java solo aparecen en tiempo de ejecución (como los temidos NullPointerException).

❌ Java — 15 líneas para un modelo de datos
public class Usuario {
  private String nombre;
  private int edad;

  // Constructor: inicializa los campos
  public Usuario(String n, int e) {
    this.nombre = n;
    this.edad = e;
  }
  // Getters: acceso a los campos privados
  public String getNombre() { return nombre; }
  public int getEdad() { return edad; }
  // Y además hay que escribir manualmente:
  // equals(), hashCode(), toString(), copy()...
}
✅ Kotlin — 4 líneas, todo incluido automáticamente
// "data class" le dice al compilador que genere
// automáticamente: equals, hashCode, toString, copy
data class Usuario(
    val nombre: String,  // val = inmutable
    val edad: Int        // tipo Int, no int
)

// Uso: copia con un campo diferente
val u1 = Usuario("Ana", 30)
val u2 = u1.copy(edad = 31)  // solo cambia edad

Kotlin — Null Safety: adiós a los NullPointerException

El error #1 en Java — resuelto por Kotlin

En Java, cualquier variable puede ser null por defecto. Esto provoca NullPointerException en producción. En Kotlin, el tipo distingue entre "puede ser null" (String?) y "nunca es null" (String). El compilador obliga a manejar el null antes de compilar.

// En Java: String puede ser null en cualquier momento
// String nombre = null;  → falla silenciosamente

// ─── En Kotlin: el tipo indica si puede ser null ───

var nombre: String = "Ana"        // ✅ nunca puede ser null
// nombre = null  → ERROR DE COMPILACIÓN ← el compilador lo detecta

var apodo: String? = null         // ✅ "?" = puede ser null explícitamente

// ── Operadores para manejar nulls de forma segura ──

// ?. = "safe call": ejecuta solo si NO es null
val largo = apodo?.length         // retorna null si apodo es null, sin crash

// ?: = "Elvis operator": valor por defecto si es null
val tamaño = apodo?.length ?: 0  // si apodo es null → retorna 0

// !! = "Non-null assertion": lanza excepción si es null
// Úsalo SOLO cuando estás seguro de que no es null
val forzado = apodo!!.length       // ⚠️ peligroso: crash si apodo es null

// ── Patrón recomendado: let ──
apodo?.let { texto ->
    // Este bloque SOLO se ejecuta si apodo != null
    // "texto" es el valor no-null dentro del bloque
    println("El apodo tiene ${texto.length} caracteres")
}
⭐ Caso real — Google estimó que el 70% de los crashes en Android son NullPointerException

Kotlin elimina esta categoría entera de bugs en tiempo de compilación, antes de que el código llegue al usuario.

Kotlin — Coroutines: concurrencia sin hilos

¿Por qué coroutines en lugar de Threads?

Un Thread es como contratar a un empleado dedicado full-time: consume memoria aunque esté esperando. Una coroutine es como un empleado que mientras espera (por red, BD) libera su espacio para que otro use ese recurso. Puedes tener miles de coroutines simultáneas con el mismo costo que 10 threads.

// ── Sin coroutines: Thread manual bloqueante ──
Thread {
    // Bloquea un hilo entero mientras espera la red
    val datos = obtenerDatosDeRed()  // bloquea
    // Para actualizar UI hay que volver al main thread
    runOnUiThread { actualizarUI(datos) }
}.start()  // crear y arrancar el thread manualmente

// ── Con coroutines: limpio y eficiente ──
// viewModelScope: se cancela automáticamente
// cuando el ViewModel se destruye
viewModelScope.launch {

    // withContext: cambia el dispatcher (hilo de ejecución)
    // Dispatchers.IO = pool de hilos para I/O (red, BD)
    val datos = withContext(Dispatchers.IO) {
        obtenerDatosDeRed()  // suspende sin bloquear
    }
    // Aquí ya estamos en el Main thread automáticamente
    actualizarUI(datos)  // seguro actualizar UI aquí
}
// ── Dispatchers: ¿en qué hilo se ejecuta? ──

// Main: hilo principal (UI) — único que puede tocar UI
Dispatchers.Main

// IO: para operaciones de entrada/salida
// (red, base de datos, archivos)
Dispatchers.IO

// Default: para cálculos intensivos (CPU)
// (ordenar listas grandes, procesar imágenes)
Dispatchers.Default

// ── async/await: ejecutar en paralelo ──
// Lanza dos operaciones simultáneamente
val a = async { obtenerUsuario() }
val b = async { obtenerProductos() }
// await() espera el resultado de cada uno
procesar(a.await(), b.await())
🏃 Metáfora

Thread = empleado dedicado que espera sentado. Coroutine = empleado que mientras espera la respuesta de un correo, hace otra tarea — mucho más eficiente.

El Modelo Mental — Imperativo vs Declarativo

🖶 Metáfora central de Compose

XML imperativo: moldear arcilla — tocas la pieza directamente para cambiar su forma. El desarrollador muta el estado del UI.
Compose declarativo: impresión 3D — describes el resultado final y la máquina lo construye cada vez que el estado cambia. Como una función matemática: mismo input → mismo output.

❌ Antes — XML + mutación directa
<!-- archivo XML separado del código Kotlin -->
<LinearLayout>
  <TextView android:id="@+id/tv"
    android:text="Hola" />
  <Button android:id="@+id/btn" />
</LinearLayout>

// Kotlin: buscar vista por ID y MUTAR su estado
val tv = findViewById<TextView>(R.id.tv)
val btn = findViewById<Button>(R.id.btn)
btn.setOnClickListener {
    // Mutamos directamente el objeto UI
    tv.text = "Mundo"  // ← mutación directa del árbol
}
✅ Compose — describe el estado, la UI se actualiza sola
@Composable  // esta función es UI declarativa
fun Saludo() {
  // Estado: cuando cambia, Compose reconstruye la UI
  var texto by remember { mutableStateOf("Hola") }

  Column {
    // Text se regenera cuando "texto" cambia
    Text(text = texto)
    Button(onClick = { texto = "Mundo" }) {
      Text("Cambiar")
    }
  }
  // Compose RECONSTRUYE solo lo que cambió — eficiente
}

ContadorApp — Tu primer Composable explicado

Conceptos clave en este ejemplo

@Composable = función de UI · remember = sobrevive recomposición · mutableStateOf = estado reactivo · by = delegado (evita .value) · Recomposición = Compose re-ejecuta la función cuando el estado cambia

// @Composable: transforma esta función en un componente de UI
// Compose la llama cada vez que su estado cambia (recomposición)
@Composable
fun ContadorApp() {

    // remember: persiste el valor entre recomposiciones
    // Sin remember → el contador se resetea a 0 en cada recomposición
    // mutableStateOf(0) → crea un observable que dispara recomposición al cambiar
    // "by" → delegado de propiedad: permite escribir "contador" en lugar de "contador.value"
    var contador by remember { mutableStateOf(0) }

    // Column: apila hijos verticalmente (equivale a LinearLayout vertical)
    // horizontalAlignment: centra todos los hijos en el eje horizontal
    Column(
        horizontalAlignment = Alignment.CenterHorizontally,
        modifier = Modifier
            .fillMaxSize()     // ocupa todo el ancho y alto disponible
            .padding(16.dp)    // margen interno de 16dp en los 4 lados
    ) {
        // Text: muestra el valor actual del estado "contador"
        // Compose reconstruye SOLO este Text cuando contador cambia
        Text(
            text = "Contador: $contador",
            style = MaterialTheme.typography.headlineMedium  // fuente M3
        )

        Spacer(modifier = Modifier.height(16.dp))  // espacio vacío de 16dp

        // Button: al hacer click ejecuta el lambda onClick
        // contador++ → cambia el estado → dispara recomposición del Text
        Button(onClick = { contador++ }) {
            Text("Incrementar")  // contenido del botón
        }
    }
}

// ¿Cómo funciona? Estado cambia → Compose compara → reconstruye solo lo necesario

Layouts — Column, Row, Box

Los 3 contenedores fundamentales de Compose

Column = apila verticalmente · Row = apila horizontalmente · Box = superpone (z-index). Son equivalentes a LinearLayout (vertical/horizontal) y FrameLayout de XML, pero con una API mucho más intuitiva.

// Column: hijos uno debajo del otro (como LinearLayout vertical)
Column(
    modifier = Modifier.fillMaxWidth().padding(16.dp),
    verticalArrangement = Arrangement.spacedBy(8.dp),   // 8dp entre hijos
    horizontalAlignment = Alignment.CenterHorizontally    // centra horizontalmente
) {
    Text("Título")
    Text("Subtítulo")
}

// Row: hijos uno al lado del otro (como LinearLayout horizontal)
Row(
    modifier = Modifier.fillMaxWidth().padding(8.dp),
    horizontalArrangement = Arrangement.SpaceBetween,  // máximo espacio entre hijos
    verticalAlignment = Alignment.CenterVertically       // centra verticalmente
) {
    Text("Izquierda")
    Text("Derecha")
}

// Box: superpone hijos (el último queda encima)
// Útil para badges, overlays, loading spinners sobre contenido
Box(modifier = Modifier.size(80.dp)) {
    Image(...)                                       // capa inferior: imagen
    Badge(modifier = Modifier.align(Alignment.TopEnd))  // capa superior: badge
}
⭐ Caso real — Twitter/X

Cada tweet usa Row (avatar + contenido), dentro hay una Column (nombre, texto, acciones), y cada botón de acción (Like, Retweet) usa Row con ícono + contador.

Modifier — El sistema de decoración de Compose

¿Qué es un Modifier y por qué el ORDEN importa?

Modifier es una cadena de decoraciones que se aplican de izquierda a derecha. Cada `.modificador()` envuelve al anterior. Esto significa que padding().clickable() ≠ clickable().padding() — el área clickeable cambia según el orden.

// Modifier: cada llamada encadena una decoración
Text(
    text = "Precio: $99",
    modifier = Modifier
        .fillMaxWidth()       // 1. ocupa todo el ancho
        .background(Color.Blue)  // 2. fondo azul (antes del padding)
        .padding(16.dp)        // 3. margen interno (sobre el fondo)
        .clip(RoundedCornerShape(8.dp))  // 4. esquinas redondeadas
        .clickable { }         // 5. área clickeable incluye el padding
)

// ⚠️ Orden incorrecto — clickeable NO incluye el padding
Modifier
    .clickable { }    // área clickeable = solo el texto
    .padding(16.dp)   // padding se añade DESPUÉS del click
// Modificadores más usados
Modifier
  .fillMaxSize()       // 100% ancho y alto
  .fillMaxWidth()      // 100% ancho
  .width(200.dp)        // ancho fijo
  .height(56.dp)        // alto fijo
  .padding(16.dp)       // margen interno todos lados
  .padding(            // margen por lado
    horizontal = 16.dp,
    vertical = 8.dp
  )
  .background(color)   // color de fondo
  .clip(shape)          // recortar forma
  .border(1.dp, color)  // borde
  .alpha(0.5f)           // transparencia 50%
  .clickable { }        // hacer clickeable
💡 Regla de oro

Piensa en Modifier como capas de CSS pero de adentro hacia afuera. El primer modificador es la capa más interior. Igual que margin vs padding en CSS.

State Hoisting — Elevar el estado

Principio: los componentes deben ser "tontos" (sin estado propio)

State hoisting = mover el estado hacia arriba en la jerarquía. El componente hijo recibe el valor y un callback. El padre es quien tiene el estado. Esto hace el componente hijo reutilizable y testeable — no importa de dónde viene el estado.

// ✅ Componente hijo "tonto": recibe todo por parámetros
// No tiene estado propio → es reutilizable en cualquier pantalla
@Composable
fun FormularioPago(
    monto: String,             // estado: viene del padre
    tarjeta: String,           // estado: viene del padre
    onMontoChange: (String) -> Unit,   // callback para notificar cambios
    onTarjetaChange: (String) -> Unit, // el hijo no cambia el estado directamente
    onPagar: () -> Unit        // callback para la acción
) {
    Column {
        OutlinedTextField(
            value = monto,
            onValueChange = onMontoChange,  // notifica al padre
            label = { Text("Monto") }
        )
        Button(onClick = onPagar) {
            Text("Pagar $$monto")
        }
    }
}
// ✅ Componente padre: DUEÑO del estado
// Centraliza toda la lógica de estado
@Composable
fun PantallaPago() {
    // El padre es quien guarda y gestiona el estado
    var monto by remember { mutableStateOf("") }
    var tarjeta by remember { mutableStateOf("") }

    // Pasa el estado hacia abajo y callbacks hacia arriba
    FormularioPago(
        monto = monto,
        tarjeta = tarjeta,
        onMontoChange = { monto = it },    // padre actualiza
        onTarjetaChange = { tarjeta = it }, // padre actualiza
        onPagar = { procesarPago(monto) }  // padre ejecuta
    )
}
⭐ Patrón real — Stripe, PayPal

Sus formularios de pago usan exactamente este patrón: el formulario es un componente sin estado propio que recibe valores y callbacks del Screen que gestiona la lógica.

¿Qué es Material 3 y por qué usarlo?

Material 3 es el sistema de diseño de Google. Define colores semánticos (primary, secondary, surface), tipografía (headlineLarge, bodyMedium) y formas. Al usarlo, tu app se adapta automáticamente al modo oscuro y a los colores del sistema del dispositivo (Material You).

Navigation Compose — Navegar entre pantallas

¿Cómo funciona la navegación en Compose?

NavController es el controlador de navegación (como un historial del browser). NavHost es el contenedor que muestra la pantalla actual. Cada pantalla tiene una ruta (string único). Navegas llamando navController.navigate("ruta").

// Paso 1: crear el NavController — gestiona el back stack
@Composable
fun AppNavigation() {
    // rememberNavController: sobrevive recomposiciones
    val navController = rememberNavController()

    // NavHost: muestra la pantalla correspondiente a la ruta actual
    NavHost(
        navController = navController,
        startDestination = "lista"  // pantalla inicial al abrir la app
    ) {

        // composable(): define una pantalla y su ruta
        composable("lista") {
            // Pasa el navController para que la pantalla pueda navegar
            PantallaLista(navController = navController)
        }

        // Ruta con argumento: {id} es un parámetro dinámico
        composable("detalle/{id}") { backStackEntry ->
            // Extraer el argumento de la ruta
            val id = backStackEntry.arguments?.getString("id") ?: ""
            PantallaDetalle(id = id, navController = navController)
        }

        composable("perfil") { PantallaPerfil(navController) }
    }
}

// Navegar desde cualquier pantalla:
navController.navigate("detalle/42")  // ir a detalle con id=42
navController.popBackStack()          // equivale al botón "Atrás"

ViewModel — Separar lógica de la UI

¿Para qué sirve el ViewModel?

El ViewModel sobrevive rotaciones de pantalla y cambios de configuración. La UI es efímera (se destruye y recrea), pero el ViewModel permanece. Esto evita perder datos al girar el teléfono. Además, separa la lógica de negocio de la UI — el ViewModel no sabe nada de Compose.

// ViewModel: sobrevive rotaciones y cambios de configuración
// No importa View, Context ni ninguna clase de Android UI
class ProductosViewModel(
    private val repositorio: ProductosRepositorio  // inyectado, no new
) : ViewModel() {

    // UiState: clase que representa TODO el estado visual de la pantalla
    // Un solo objeto en lugar de múltiples variables sueltas
    data class UiState(
        val productos: List<Producto> = emptyList(),  // lista vacía por defecto
        val cargando: Boolean = true,                 // inicia cargando
        val error: String? = null                      // null = sin error
    )

    // MutableStateFlow: flujo de datos mutable INTERNO (privado)
    private val _uiState = MutableStateFlow(UiState())
    // StateFlow: versión de solo lectura expuesta a la UI
    val uiState: StateFlow<UiState> = _uiState.asStateFlow()

    init {
        cargarProductos()  // cargar datos al crear el ViewModel
    }

    private fun cargarProductos() {
        // viewModelScope: coroutine que se cancela cuando el ViewModel muere
        viewModelScope.launch {
            try {
                val lista = repositorio.obtenerProductos()
                // copy(): actualiza solo los campos que cambian
                _uiState.update { it.copy(productos = lista, cargando = false) }
            } catch (e: Exception) {
                _uiState.update { it.copy(error = e.message, cargando = false) }
            }
        }
    }
}

ViewModel — Conectar con la UI

Flujo completo: ViewModel → StateFlow → collectAsStateWithLifecycle → UI

collectAsStateWithLifecycle() observa el StateFlow de forma segura: deja de escuchar cuando la app va al background (ahorra batería) y reanuda cuando vuelve al primer plano. Siempre úsalo en lugar de collectAsState().

// La UI observa el ViewModel — nunca crea lógica aquí
@Composable
fun PantallaProductos(
    // viewModel() obtiene la instancia del ViewModel (sobrevive rotaciones)
    viewModel: ProductosViewModel = viewModel()
) {
    // collectAsStateWithLifecycle: convierte Flow en State de Compose
    // Se pausa cuando la app va al background para ahorrar batería
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    // Mostrar contenido según el estado actual
    when {
        // Caso 1: está cargando → mostrar indicador
        uiState.cargando -> CircularProgressIndicator()

        // Caso 2: hay error → mostrar mensaje
        uiState.error != null -> Text("Error: ${uiState.error}")

        // Caso 3: datos listos → mostrar lista
        else -> LazyColumn {
            // items(): función de extensión de LazyColumn
            items(uiState.productos) { producto ->
                TarjetaProducto(producto = producto)
            }
        }
    }
}
⭐ Caso real — Netflix

La pantalla principal de Netflix tiene un UiState con: lista de contenido, estado de carga, y perfil del usuario. Cuando rotas el teléfono, el ViewModel persiste y no recarga el contenido de red.

LazyColumn — Listas eficientes (equivale a RecyclerView)

¿Por qué Lazy? — Solo renderiza lo visible en pantalla

Column renderiza todos los elementos al mismo tiempo, aunque no sean visibles. LazyColumn solo renderiza los elementos visibles (como RecyclerView), lo que lo hace eficiente para miles de elementos.

// LazyColumn: equivalente a RecyclerView — solo renderiza lo visible
LazyColumn(
    modifier = Modifier.fillMaxSize(),
    // contentPadding: padding alrededor de toda la lista
    contentPadding = PaddingValues(horizontal = 16.dp, vertical = 8.dp),
    // verticalArrangement: espacio entre elementos
    verticalArrangement = Arrangement.spacedBy(8.dp)
) {
    // item(): un solo elemento fijo (ej: encabezado)
    item { Text("Productos destacados", style = MaterialTheme.typography.titleLarge) }

    // items(lista): genera un elemento por cada objeto de la lista
    // key: identificador único para que Compose haga diff eficiente
    items(productos, key = { it.id }) { producto ->
        TarjetaProducto(
            producto = producto,
            onClick = { navController.navigate("detalle/${producto.id}") }
        )
    }

    // itemsIndexed: cuando también necesitas el índice
    itemsIndexed(productos) { index, producto ->
        Text("${index + 1}. ${producto.nombre}")
    }

    // item(): pie de lista
    item { Spacer(Modifier.height(80.dp)) }  // espacio para el FAB
}

Room — Base de datos local en Android

¿Qué es Room y cómo se estructura?

Room es una capa de abstracción sobre SQLite. Tiene 3 componentes: @Entity = tabla de la BD (una clase Kotlin = una tabla), @Dao = operaciones (queries como funciones Kotlin), @Database = punto de entrada a la BD.

// @Entity: define una TABLA en la base de datos
// tableName: nombre de la tabla en SQLite (opcional)
@Entity(tableName = "productos")
data class ProductoEntity(

    // @PrimaryKey: llave primaria de la tabla
    // autoGenerate: Room asigna el ID automáticamente
    @PrimaryKey(autoGenerate = true)
    val id: Int = 0,

    // @ColumnInfo: personaliza el nombre de la columna
    // Sin esto, el nombre de la columna = nombre de la propiedad
    @ColumnInfo(name = "nombre_producto")
    val nombre: String,

    val precio: Double,     // columna "precio"
    val stock: Int = 0,     // columna "stock", valor por defecto 0
    val enOferta: Boolean = false
)
// @Dao: define las OPERACIONES sobre la tabla
// Dao = Data Access Object — solo queries, no lógica
@Dao
interface ProductoDao {

    // Flow<List>: retorna datos en tiempo real
    // Cada vez que los datos cambian, Room emite la nueva lista
    @Query("SELECT * FROM productos ORDER BY nombre")
    fun obtenerTodos(): Flow<List<ProductoEntity>>

    // suspend: operación asíncrona que no bloquea el hilo
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertar(producto: ProductoEntity)

    // @Delete: borra el registro que coincide con el objeto
    @Delete
    suspend fun eliminar(producto: ProductoEntity)

    // Query con parámetro: :id coincide con el parámetro "id"
    @Query("SELECT * FROM productos WHERE id = :id")
    suspend fun obtenerPorId(id: Int): ProductoEntity?
}

// @Database: declara la base de datos Room
// entities: lista de todas las tablas
// version: incrementar al cambiar el esquema
@Database(entities = [ProductoEntity::class], version = 1)
abstract class AppDatabase : RoomDatabase() {

    abstract fun productoDao(): ProductoDao

        @Volatile private var INSTANCE: AppDatabase? = null

                Room.databaseBuilder(

                    AppDatabase::class.java,
                    "app_database.db"  // nombre del archivo
                ).build().also { INSTANCE = it }
            }
        }
    }

Retrofit — Cliente HTTP moderno con Coroutines

¿Qué es Retrofit y cómo funciona con suspend?

Retrofit convierte interfaces Kotlin en llamadas HTTP. Con suspend fun, la llamada de red se ejecuta de forma asíncrona sin bloquear el hilo principal. Combina con sealed class para manejar los estados: Cargando, Éxito y Error.

// Interfaz Retrofit: cada función = un endpoint HTTP
interface ProductosApi {

    // @GET: petición GET a la URL relativa
    // suspend: la función es asíncrona (no bloquea el hilo)
    @GET("productos")
    suspend fun obtenerProductos(): RespuestaProductos

    // @Path: sustituye {id} en la URL con el valor del parámetro
    @GET("productos/{id}")
    suspend fun obtenerProducto(@Path("id") id: Int): ProductoDto

    // @Query: añade parámetros a la URL: ?pagina=1&limite=20
    @GET("productos")
    suspend fun buscar(
        @Query("q") termino: String,
        @Query("pagina") pagina: Int = 1
    ): RespuestaProductos

    // @Body: envía el objeto como JSON en el cuerpo del POST
    @POST("productos")
    suspend fun crearProducto(@Body producto: ProductoDto): ProductoDto
}
// Sealed class: representa los 3 estados posibles de una operación
// Fuerza al código a manejar TODOS los casos (exhaustivo)
sealed class Resultado<out T> {
    // Éxito: contiene los datos
    data class Exito<T>(val datos: T) : Resultado<T>()
    // Error: contiene el mensaje de error
    data class Error(val mensaje: String) : Resultado<Nothing>()
    // Cargando: estado intermedio
    object Cargando : Resultado<Nothing>()
}

// Uso en ViewModel con when exhaustivo
when (val resultado = repositorio.obtenerProductos()) {
    is Resultado.Exito   -> mostrar(resultado.datos)
    is Resultado.Error   -> mostrarError(resultado.mensaje)
    is Resultado.Cargando -> mostrarSpinner()
    // No hay "else" — sealed class garantiza que son solo estos 3
}

Patrón Offline-First — Repository

¿Qué es offline-first y por qué es importante?

Una app offline-first siempre muestra datos de la BD local primero. Luego sincroniza con la red en background. El usuario ve datos instantáneamente y no depende de conexión. Spotify, Gmail y WhatsApp funcionan así.

// ProductosRepositorioImpl: coordina BD local y API remota
// Regla offline-first: BD es la fuente de verdad
class ProductosRepositorioImpl(
    private val dao: ProductoDao,       // fuente local (Room)
    private val api: ProductosApi       // fuente remota (Retrofit)
) : ProductosRepositorio {

    // obtenerProductos(): Flow que emite la lista de la BD
    // Cada vez que Room actualiza la BD, la UI recibe la nueva lista
    // Sin necesidad de llamar manualmente a "recargar"
    override fun obtenerProductos(): Flow<List<Producto>> =
        dao.obtenerTodos()              // retorna Flow de Room directamente
           .map { entities -> entities.map { it.toProducto() } }

    // sincronizar(): descarga de la red y guarda en BD local
    // La UI no llama a esto — usa el Flow de arriba
    override suspend fun sincronizar() {
        // withContext(IO): cambia al hilo de IO para operaciones de red
        withContext(Dispatchers.IO) {
            try {
                // Paso 1: descargar de la API
                val remotos = api.obtenerProductos().productos

                // Paso 2: guardar en Room — Room actualiza el Flow automáticamente
                dao.insertarTodos(remotos.map { it.toEntity() })

                // El Flow de obtenerProductos() emitirá la nueva lista sin
                // que la UI tenga que pedir los datos de nuevo
            } catch (e: IOException) {
                // Sin conexión: mostrar datos de la BD local (offline-first)
                // No lanzamos el error — la UI ya tiene datos cacheados
            }
        }
    }
}

WorkManager — Trabajo garantizado en background

¿Cuándo usar WorkManager?

WorkManager garantiza que el trabajo se ejecute aunque el usuario cierre la app o reinicie el dispositivo. Ideal para: subir fotos, sincronizar datos, enviar logs. No es para trabajo inmediato (usa coroutines) ni para notificaciones push (usa FCM).

// CoroutineWorker: worker moderno con soporte de coroutines
// Siempre usar CoroutineWorker en lugar de Worker
class SincronizacionWorker(
    context: Context,
    params: WorkerParameters
) : CoroutineWorker(context, params) {

    // doWork: función suspendida que realiza el trabajo
    // Se ejecuta en Dispatchers.Default automáticamente
    override suspend fun doWork(): Result {
        return try {
            val repo = (applicationContext as MiApp).repositorio
            repo.sincronizar()
            Result.success()  // trabajo completado exitosamente

        } catch (e: IOException) {
            // Sin red: reintentar automáticamente
            // runAttemptCount: número de intentos realizados
            if (runAttemptCount < 3) Result.retry()  // reintentar
            else Result.failure()                    // fallar después de 3 intentos
        }
    }
}

            .setRequiresBatteryNotLow(true)                // no con batería baja
            .build()
    ).build()

// enqueueUniquePeriodicWork: evita duplicados con la misma "clave"

Patrón AAA: Arrange → Act → Assert

// @ExtendWith: activa la extensión de MockK para JUnit 5
@ExtendWith(MockKExtension::class)
class ProductosViewModelTest {

    // @MockK: crea un objeto falso que simula el repositorio real
    @MockK private lateinit var repositorio: ProductosRepositorio

    @Before
    fun setup() {
        // Reemplaza Dispatchers.Main por uno síncrono para tests
        // Sin esto, las coroutines del ViewModel no se ejecutan en tests
        Dispatchers.setMain(StandardTestDispatcher())
    }

    @After
    fun tearDown() { Dispatchers.resetMain() }  // restaurar para otros tests

    @Test
    fun `cuando se cargan productos uiState tiene la lista`() = runTest {
        // ── ARRANGE: configurar el mock ──
        val esperados = listOf(Producto(1, "Laptop", 999.99))
        // coEvery: cuando se llame a obtenerProductos(), retorna este Flow
        coEvery { repositorio.obtenerProductos() } returns flowOf(esperados)

        // ── ACT: crear el ViewModel (dispara init → cargarProductos) ──
        val viewModel = ProductosViewModel(repositorio)

        // ── ASSERT: verificar el estado usando Turbine ──
        // .test(): colector de Flow para tests — captura emisiones
        viewModel.uiState.test {
            val estado = awaitItem()  // espera la próxima emisión del Flow
            assertThat(estado.productos).isEqualTo(esperados)
            assertThat(estado.cargando).isFalse()
            cancelAndIgnoreRemainingEvents()  // limpiar
        }
    }
}

fun AppNavigation() {

    val nav = rememberNavController()

    NavHost(nav, startDestination = "home") {

                    // navigate("detalle/$id") inserta la pantalla en el back stack
                    nav.navigate("detalle/$id")
                }
            )
        }

        composable("nueva") {
            NuevaIncidenciaScreen(

                onGuardar = { nav.popBackStack() },

// IncidenciasViewModel.kt — sobrevive rotaciones de pantalla
// @HiltViewModel: le dice a Hilt que este ViewModel usa inyección de dependencias
@HiltViewModel
// @Inject constructor: Hilt construye el objeto automáticamente
// En Fase 1 no hay repositorio; en Fase 3 se inyecta IncidenciaRepositorio
class IncidenciasViewModel @Inject constructor() : ViewModel() {

    // MutableStateFlow: flujo de datos mutable — al cambiar, notifica a la UI
    // private: solo este ViewModel puede modificarlo (encapsulación)
    // emptyList(): estado inicial = lista vacía, no null
    private val _incidencias = MutableStateFlow<List<Incidencia>>(emptyList())

    // asStateFlow(): expone versión de solo lectura a la UI
    // La UI observa este, pero no puede modificarlo directamente
    val incidencias = _incidencias.asStateFlow()

    fun agregar(inc: Incidencia) {
        // copy(): crea nueva instancia cambiando solo el campo "id"
        // size + 1 es un ID temporal; Room generará IDs reales en Fase 3
        val nueva = inc.copy(id = (_incidencias.value.size + 1))
        // update { }: recibe la lista actual y retorna la nueva lista
        // "it + nueva" = concatenar la nueva incidencia al final de la lista
        _incidencias.update { it + nueva }
    }

    // find { }: recorre la lista y devuelve el primer elemento que cumpla
    // la condición; devuelve null si no lo encuentra (por eso retorna Incidencia?)
    fun obtenerPorId(id: Int): Incidencia? =
        _incidencias.value.find { it.id == id }

    fun cambiarEstado(id: Int, estado: Estado) {
        _incidencias.update { lista ->
            // map { }: transforma cada elemento de la lista
            // Si el id coincide → crea copia con nuevo estado
            // Si no coincide → devuelve el elemento sin cambios
            lista.map { if (it.id == id) it.copy(estado = estado) else it }
        }
    }
}

Enriquecer el reporte con evidencia fotográfica

CameraX envuelve la API de cámara de Android. Usamos suspendCancellableCoroutine para convertir su callback en una función suspend limpia.

// CameraHelper.kt — envuelve CameraX en una API suspend amigable
class CameraHelper(
    private val context: Context,
    // LifecycleOwner: CameraX observa el ciclo de vida y libera la cámara
    // automáticamente cuando la pantalla se destruye — evita fugas de recursos
    private val lifecycleOwner: LifecycleOwner
) {
    // ImageCapture: caso de uso de CameraX para capturar fotos
    // MINIMIZE_LATENCY: prioriza velocidad sobre calidad de imagen
    private val imageCapture = ImageCapture.Builder()
        .setCaptureMode(ImageCapture.CAPTURE_MODE_MINIMIZE_LATENCY)
        .build()

    // suspend: la función se puede pausar sin bloquear el hilo principal
    // Uri?: retorna la ruta del archivo guardado, o null si hubo error
    suspend fun tomarFoto(): Uri? = suspendCancellableCoroutine { cont ->
        // suspendCancellableCoroutine: puente entre callback antiguo y coroutine
        // "cont" es la continuación — llamar cont.resume() despierta la coroutine

        // filesDir: directorio privado de la app (no accesible a otras apps)
        // currentTimeMillis() en el nombre garantiza nombres únicos de archivo
        val archivo = File(context.filesDir,
            "incidencia_${System.currentTimeMillis()}.jpg")

        // OutputFileOptions: indica a CameraX dónde guardar la foto
        val options = ImageCapture.OutputFileOptions.Builder(archivo).build()

        // takePicture: inicia la captura de forma asíncrona
        // getMainExecutor: el callback se ejecuta en el hilo principal
        imageCapture.takePicture(options, ContextCompat.getMainExecutor(context),
            object : ImageCapture.OnImageSavedCallback {
                override fun onImageSaved(output: OutputFileResults) {
                    // Foto guardada: convertimos File a Uri y despertamos la coroutine
                    cont.resume(Uri.fromFile(archivo))
                }
                override fun onError(e: ImageCaptureException) {
                    // Error al capturar: devolvemos null, el ViewModel decide qué mostrar
                    cont.resume(null)
                }
            })
    }
}

// LocationHelper.kt — usa Fused Location (fusiona GPS + WiFi + red móvil)
// Fused API elige automáticamente la fuente más precisa y eficiente
class LocationHelper(private val context: Context) {

    // FusedLocationProviderClient: cliente que Google Play Services gestiona
    // — más preciso que GPS solo y consume menos batería
    private val client = LocationServices
        .getFusedLocationProviderClient(context)

    // @SuppressLint: ya verificamos el permiso antes de llamar a esta función
    // Android Studio muestra error si no suprimimos — le decimos que lo sabemos
    @SuppressLint("MissingPermission")
    suspend fun obtenerUbicacion(): Location? =
        suspendCancellableCoroutine { cont ->
            // PRIORITY_HIGH_ACCURACY: usa GPS (más preciso, más batería)
            // PRIORITY_BALANCED_POWER_ACCURACY usa WiFi/red (menos preciso, menos batería)
            // null = sin token de cancelación externo
            client.getCurrentLocation(Priority.PRIORITY_HIGH_ACCURACY, null)
                // addOnSuccessListener: se llama cuando se obtiene la ubicación
                // "it" es el objeto Location con latitude y longitude
                .addOnSuccessListener { cont.resume(it) }
                // addOnFailureListener: GPS desactivado o sin permiso → devuelve null
                .addOnFailureListener { cont.resume(null) }
        }
}

// data/remote/FirestoreRepository.kt — sincroniza con Firebase
class FirestoreRepository(
    private val db: FirebaseFirestore,   // base de datos NoSQL en la nube
    private val auth: FirebaseAuth,       // autenticación de usuarios
    private val storage: FirebaseStorage  // almacenamiento de archivos (fotos)
) {
    // collection("incidencias"): referencia a la colección en Firestore
    // En NoSQL una "colección" equivale a una tabla, un "documento" a una fila
    private val col = db.collection("incidencias")

    suspend fun subir(inc: Incidencia): Boolean {
        return try {
            // currentUser?.uid: ID único del usuario autenticado
            // ?: return false: si no hay usuario logueado, abortamos sin subir
            val uid = auth.currentUser?.uid ?: return false

            // fotoUri?.let { }: solo se ejecuta si fotoUri NO es null (Fase 2+)
            val fotoUrl = inc.fotoUri?.let { uri ->
                // child("fotos/uid/id.jpg"): ruta única en Firebase Storage por usuario
                // putFile(): sube el archivo local al Storage — await() espera sin bloquear
                // downloadUrl: URL pública con la que Firestore referencia la foto
                storage.reference.child("fotos/$uid/${inc.id}.jpg")
                    .putFile(Uri.parse(uri)).await()
                    .storage.downloadUrl.await().toString()
            }

            // document(id): selecciona o crea el documento con ese ID
            // set(): guarda el objeto completo (sobreescribe si ya existe)
            // await(): suspende hasta que Firestore confirma la escritura
            col.document(inc.id.toString()).set(
                inc.copy(fotoUri = fotoUrl, sincronizado = true)
            ).await()
            true  // éxito: el Worker marcará la fila en Room como sincronizada

        } catch (e: Exception) { false }  // sin red → false, Worker reintentará
    }

    // Firebase Auth con Google — el idToken viene del selector de cuenta de Google
    suspend fun loginConGoogle(idToken: String): Boolean {
        // GoogleAuthProvider.getCredential: convierte el token de Google en credencial Firebase
        val cred = GoogleAuthProvider.getCredential(idToken, null)
        return try {
            // signInWithCredential: valida con Firebase y crea la sesión del usuario
            auth.signInWithCredential(cred).await()
            true
        } catch (e: Exception) { false }
    }
}

// SyncWorker.kt — Worker que garantiza la ejecución aunque la app esté cerrada
// CoroutineWorker: versión moderna que soporta suspend functions nativamente
class SyncWorker(ctx: Context, params: WorkerParameters)
    : CoroutineWorker(ctx, params) {

    // doWork(): función principal del worker — se ejecuta en Dispatchers.Default
    // WorkManager la llama cuando se cumplen las constraints (hay red)
    override suspend fun doWork(): Result {
        // applicationContext: acceso a la instancia global de la app
        // "as CityReportApp" hace cast para acceder a dao y firestoreRepo
        val app = applicationContext as CityReportApp

        // Consultamos Room: incidencias con sincronizado = false
        val pendientes = app.dao.obtenerNoSincronizadas()
        // Si no hay nada pendiente → éxito inmediato, no consumimos red
        if (pendientes.isEmpty()) return Result.success()

        return try {
            pendientes.forEach { entity ->
                // toIncidencia(): convierte Entity (capa datos) → Incidencia (dominio)
                val ok = app.firestoreRepo.subir(entity.toIncidencia())
                // Solo marca como sincronizada si Firestore confirmó la escritura
                if (ok) app.dao.marcarSincronizada(entity.id)
            }
            Result.success()  // todo subido correctamente
        } catch (e: IOException) {
            // runAttemptCount: cuántas veces WorkManager ha intentado este trabajo
            // retry(): WorkManager vuelve a intentarlo con backoff exponencial
            // failure(): después de 3 intentos fallidos, desiste
            if (runAttemptCount < 3) Result.retry() else Result.failure()
        }
    }
}

// Programar el worker — se lanza desde el ViewModel al detectar incidencias pendientes
// OneTimeWork (no periódico): se ejecuta una vez cuando vuelve la red
val syncRequest = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(Constraints.Builder()
        // CONNECTED: WorkManager espera automáticamente a que haya red
        .setRequiredNetworkType(NetworkType.CONNECTED)
        .build())
    .build()

// enqueueUniqueWork con nombre "city_sync": evita duplicados
// ExistingWorkPolicy.REPLACE: si ya hay un worker esperando, lo reemplaza
WorkManager.getInstance(context)
    .enqueueUniqueWork("city_sync", ExistingWorkPolicy.REPLACE, syncRequest)
